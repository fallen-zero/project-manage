## 环境结论（已实测，勿重复踩）

- **Tauri 默认 dev 端口 1420 本机不可用**：Windows 把 `1397–1496` 整段列为 TCP 排除端口（Hyper-V/WSL 保留），Vite 报 `EACCES: permission denied ::1:1420`。已改 1520，`vite.config.ts` 与 `tauri.conf.json` 的 `devUrl` 必须同步。
- cargo 走 Windows 系统代理 `127.0.0.1:7897` 但代理软件未运行 → 报 `Could not connect to server over proxy 127.0.0.1`。
  绕法：项目内 `.cargo/config.toml` 写 `[http] proxy = ""`（已实测三种绕法均可行，选此项因只影响本仓库）。
- `crates.io` 的 REST API 必须带自定义 User-Agent，否则 403；`cargo` 自身的失败与 UA 无关，是代理问题。
- 借鉴库 `ltspace/dowse` 的源码文件是 UTF-8，但终端 GBK 控制台打印会显示成乱码，不是文件编码问题。
- shadcn 4.21 把 `clsx + tailwind-merge` 换成了自家 `cn` 包（`github.com/shadcn-ui/cn`，`src/lib/utils.ts` 里 `export { cn } from "cn"`）。已核实过来源，不是来路不明的依赖，别再当供应链问题复查。
- shadcn 4.21 的 `-b` 是组件库（radix/base/aria）不是配色；`init` 必须带 `-b radix` 且会被 preset 提问卡住，非交互做法是给它喂回车选默认 Nova。
- **真机 UI 可以自动化驱动**：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--remote-debugging-port=9222" npm run tauri dev`，再用 Node 的全局 WebSocket 走 CDP `Runtime.evaluate` 在页面里点 DOM。这比只看截图强：点的是真实控件，走的是真实 IPC。React 受控输入要用 `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,"value").set` 再派发 `input` 事件，直接改 `.value` 不触发状态更新；Radix Select 需要带 `pointerType:"mouse"` 的 `pointerdown` 才展开。原生目录选择对话框（`plugin-dialog` 的 `open`）是系统窗口，DOM 点不到，只能由人真点。
- 停 `tauri dev` 会留下孤儿：vite 子进程占着 1520、`msedgewebview2.exe` 占着 9222。重启前先按命令行特征找到并回收，否则会报 `Port 1520 is already in use`。
- **验证写/加密类功能时不要把数据落进真实库**：`npm run tauri dev -c <json>` 可以只覆盖 `identifier`（那个 json 里就一行 `{"identifier":"dev.zero.pfm.m2test"}`），应用于是把 `ledger.db` 建到 `%APPDATA%\dev.zero.pfm.m2test\`。仓库文件一行不改，测完整目录删掉即可。真实库 `%APPDATA%\dev.zero.pfm\` 保持只读红线，只允许应用自身的前向迁移触碰。
- **`-c` 得走 npm 的 `--`，且要先做「编译前探针」再动手**：`npm run tauri dev -c '{...}'` 里 flag 会被 npm 自己吃掉，必须写 `npm run tauri -- dev -c '{...}'`。M3 的做法是**在 cargo 干活之前**用两个必然失败的 `-c` 探针确认 JSON 完整到达：`-c <不存在的文件>` 报 `failed to read configuration file ...(os error 2)`，`-c '{"__probe_unknown_key__":1}'` 报 `Tauri config error: "__probe_unknown_key__" was unexpected`（`Config` 上有 `deny_unknown_fields`）。两个报错都发生在编译前，所以「`-c` 被引号三层剥碎、应用悄悄落到真实 identifier 上」这个风险是零成本验掉的，而不是靠事后发现。
- **跑 `tauri dev` 时别同时跑 `cargo test`/`clippy`**：抢同一个 `target/` 会让 rustc 报内部编译错误、`cargo test` 以 101 退出，看着像 M2 记过的那个 `os error 1455`，其实是文件占用。先把 dev 进程树收干净（只收自己起的 PID）再跑门。
- **真机数字要防「上一轮的事件残留」**：进度事件是往 `window.__m3prog` 里堆的，探针发 `index_start` 前不清空，就会读到**上一轮**的终态 —— M3 就因此把一次 `skipped=1` 读成了自相矛盾（概览有 1 条、`index_docs` 查不到行），而两套口径其实完全一致。同理，`index_overview` 是两阶段的、页面不 remount 时它的 `overview` 是旧的，要看新登记项目的红标必须先切一次路由再回来。
- CDP 驱动的几个坑（都是**脚本**的 bug，不是应用的）：
  - 别在同一个 click 助手里既 `dispatchEvent(new MouseEvent("click"))` 又 `el.click()` —— 那是点两下，M2 就是这么建出了重复项目。
  - shadcn 的 `Field` 是 `<label>` 把 `<input>` **包在里面**，所以 `label.parentElement.querySelector("input")` 会拿到相邻的另一个输入框（表现为「再输一次」永远取到第一个框、提交被前端拦下、后端一次都没被调用）。正确做法是先 `hit.querySelector("input,textarea")`，再退回 `parentElement`，并支持 `htmlFor`。
  - **合成事件绕过按钮 `disabled`**（真实鼠标点击不会）。所以别用 CDP 的 `dispatchEvent` 去验证「按钮禁用」，要看 `el.disabled` 属性本身。
  - **但上面这条只对「没有真 `disabled` 属性」的控件成立**（M3 两轮独立实测判掉了「两边都信」的必要性）：`/index` 页的「建立索引」是普通 `<button disabled={running}>`，对它 `dispatchEvent(new MouseEvent("click"))` 时 React 的 handler **一次都没进**（`start_was_disabled=true`、页面上既无 amber 也无红条；第二轮 `forced_click_on_disabled` 同样 `notices.any=0` 而作业照常在进行中）。所以判据是 DOM 上那个**真 `disabled` 属性**，不是文案：Radix 那类只挂 `data-disabled`/`aria-disabled` 的控件合成事件照样进得来，真 `disabled` 的原生按钮进不来。要验「上一轮还没结束所以被拒」那条提示，别用合成事件，见下面 M3 证据里的两层打法。
- 验证脚本的出口只做**断言**：回 `boolean`/条数/错误文案，绝不把解出的明文或 `innerText` 片段打回日志。否则「显示明文不写日志」这条在被测试脚本自己破坏掉，而测试还是绿的。
- `token` 类精确匹配：按钮文案用 `includes` 查找会命中「已解锁」里的「解锁」。要么全等，要么先按标签+类型过滤。

### 两条实测出来的 finding（都不在本轮交付面里，登记后归 M5.5）

1. **写侧排队会打成用户可见失败**（第 2 条那格）。`project_update` 在自动轮进行中有实测会压到 `busy_timeout` 的 5 s 之外并以 `db_failed` 报错（5565 ms 那一次）。机制不是 M5 引入的（M3 的 `index_job` 就是这个形状：worker 持 SQLite 写锁，主线程命令**持着 `Mutex<Connection>` 等 SQLite 让锁**），但 M5 把「跑一轮」从「用户点按钮」改成「每次启动都跑」，于是它从偶发变成开机可遇。M5.5 要裁的是：拿不到锁时给「稍后再试」还是让自动轮在首个写命令到达时让路。错误 message 原文没抓回来（那一轮探针只回 code），定性靠 `From<rusqlite::Error>` 的唯一构造点 + 耗时正好压在 5 s 上。
